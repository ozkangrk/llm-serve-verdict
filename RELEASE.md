# Release process

Release process for **Serving Verdict**. This document is the operator's
guide to (a) producing a release, (b) verifying one, and (c) setting up and
checking the branch-protection settings that make the release pipeline
trustworthy. It documents **repository automation only** — nothing here
modifies remote settings automatically.

See `THREAT_MODEL.md` for the threat model and claim boundary, and
`SECURITY.md` for vulnerability reporting.

## 1. What a release contains

A `vX.Y.Z` tag on a commit of `main` triggers `.github/workflows/release.yaml`,
which produces and attaches to the GitHub Release:

| Asset | What it proves |
|---|---|
| `serving_verdict-X.Y.Z-py3-none-any.whl` | installable distribution |
| `serving-verdict-X.Y.Z.tar.gz` | source distribution |
| `SHA256SUMS` | SHA-256 digests of the wheel and sdist, generated and self-checked (`sha256sum -c`) in the build job before upload |
| *(GitHub artifact attestation)* | DSSE provenance statements for the assets, generated by `actions/attest-build-provenance` in the same build job, linking them to the exact source commit and workflow run |

**Claim boundary (do not weaken).**

- Attestation is **GitHub artifact provenance** only. It is *not* a
  Sigstore/cosign signature, not an OIDC signer identity beyond what GitHub's
  attestation service provides, and not a certificate.
- Builds are **not reproducible bit-identical** across machines/toolchains.
  Verify by `SHA256SUMS` (integrity) + attestation (commit/run linkage), not
  by rebuilding and comparing bytes.
- PyPI publication is a separate, explicitly guarded path
  (`publish-pypi.yaml`, trusted publishing, manual dispatch or tag +
  configured trusted publisher). It is intentionally out of scope for the
  default release and is skipped unless the operator has configured the
  trusted publisher (see `docs/release-checklist.md` §6).

## 2. Pre-release gates (local, then CI)

Run these in the release branch working tree **and** in a fresh clone:

```bash
uv sync --extra dev
uv run pytest -q                      # full test suite (offline)
uv run ruff check src tests
uv run mypy src
uv run python scripts/check_workflows.py   # workflow pinning/permissions/contracts
uv build                              # sdist + wheel
```

Gate contract (machine-checked by `scripts/check_workflows.py`, which runs in
CI):

1. **Version consistency** — `pyproject.toml` `version`, runtime
   `serving_verdict.__version__`, and the `CHANGELOG.md` `## [X.Y.Z]` entry
   must all be identical.
2. **Workflow security** — every `.github/workflows/*.y*ml` must:
   - parse as YAML,
   - declare an explicit least-privilege `permissions:` map matching the
     policy in `MAX_PERMISSIONS` (no wildcards, no `admin`, no unlisted
     scopes),
   - reference third-party actions only by 40-hex commit SHAs that appear in
     the verified `PINNED_REFS` registry (floating `@v*`/branch refs fail).
3. **Release contract** — `release.yaml` must generate `SHA256SUMS`,
   self-check it, attach it to the release, attest provenance, and fail when
   the tag does not match `pyproject.toml`.

## 3. Cutting a release

1. On the release branch, update `CHANGELOG.md`: move `Unreleased` items into
   `## [X.Y.Z] — YYYY-MM-DD` and set honest limitations.
2. Bump `version` in `pyproject.toml` and `__version__` in
   `src/serving_verdict/__init__.py` to `X.Y.Z` (identical).
3. Run the §2 gates locally; confirm
   `python scripts/check_workflows.py` prints all-green.
4. Merge to `main` through a pull request (required reviews + required CI
   per §4). Do **not** push to `main` directly (enforced by branch
   protection).
5. Create and push an annotated tag on the merged commit:

   ```bash
   git tag -a vX.Y.Z -m "vX.Y.Z"
   git push origin vX.Y.Z
   ```

6. Watch the `Release` workflow: tag/version gate → pytest → ruff → mypy →
   workflow audit → build → wheel import → `SHA256SUMS` (generated +
   `sha256sum -c`) → attestation → GitHub Release with assets.
   Prerelease tags (`X.Y.Z-rc1` …) are marked prerelease automatically.

## 4. Branch protection — setup (operator action)

The pipeline *assumes* the following; none of it is created by code. An
operator with admin access configures it once in
**GitHub → repository → Settings → Branches → Add branch rules** (rule name:
`main`):

- **Protect matching branch**: `main`.
- **Require pull request reviews before merging**: ≥ 1 (more if desired).
- **Require status checks to pass before merging** — select:
  - `test (ubuntu-latest, py3.11)` / `test (ubuntu-latest, py3.12)` (CI),
  - `CodeQL / analyze (python)`,
  - `Dependency Audit / audit (uv, frozen lockfile)`,
  - `Secret Scan / gitleaks (full history)`.
- **Include administrators for required reviews and status checks**: yes
  (recommended; otherwise admins can bypass the release gates).
- **Do not allow force pushes**: on.
- **Do not allow deletions**: on.
- **Require signed commits**: optional (policy choice; the project does not
  depend on commit GPG signatures).

Also configure:

- **Settings → Code and automation → Actions → workflows**: ensure the
  pinned-action workflows run on PRs from forks with read-only GITHUB_TOKEN
  (the default). Our workflows never require write tokens on forks.
- **PyPI trusted publishing** (only if publishing to PyPI): Settings →
  Developer settings → OIDC → add audience `https://pypi.org`, plus the PyPI
  trusted publisher for `serving-verdict` with subject
  `repository:ozkangrk/serving-verdict`, workflow `publish-pypi.yaml`,
  environment `pypi`. Until then, PyPI is skipped by design.

> ⚠️ These are **manual, one-time repository settings**. The repository
> code and workflows do not, and must not, modify remote settings.

## 5. Branch protection — check (verification)

Verify the settings without changing them:

```bash
# Requires `gh` authenticated with admin access to the repository.
# Read-only: inspects rules, never mutates them.
gh api repos/ozkangrk/serving-verdict/branches/main/protection --jq '
  {
    required_pull_request_reviews: .required_pull_request_reviews,
    required_status_checks: .required_status_checks,
    enforced_admins: .enforced_admins,
    restrictions: (.restrictions and {users: (.users | length), apps: (.apps | length)})
  }'
# List the currently required status checks by name:
gh api repos/ozkangrk/serving-verdict/branches/main/protection/required_status_checks --jq '.[].context'
```

Checklist:

- [ ] `required_status_checks.strict == true` and the contexts include the
      four jobs named in §4.
- [ ] `required_pull_request_reviews` exists (≥ 1) and `enforced_admins` is
      enabled.
- [ ] `allow_force_pushes == false`, `allow_deletions == false` (absent keys
      mean the restrictive defaults — confirm in the UI).
- [ ] Manual smoke test: a PR from a scratch branch to `main` without the
      required checks configured cannot be merged; with them configured,
      merge is blocked until all four checks pass.
- [ ] Tags: confirm the `v*` tag pushes are still permitted (tag pushes do
      not go through PR review; the release gates live in `release.yaml`
      itself — version gate, tests, workflow audit, attestation).

## 6. Post-release verification (operator)

1. GitHub Release contains the wheel, sdist, `SHA256SUMS`, notes, and (for
   new GitHub-attested releases) an attestation visible on the run's
   artifacts / the release page.
2. Recompute digests independently:

   ```bash
   sha256sum -c SHA256SUMS        # after downloading the assets
   ```

3. Install from the downloaded wheel into a clean venv and check
   `serving_verdict.__version__` equals the release version.
4. Record in the release notes: tag → commit SHA, CI run URL, and the
   `SHA256SUMS` contents.
5. Keep prior tags immutable. Fix automation for the next release; never
   move a published tag.

## 7. If a release must be retracted

- Do not move the tag. Publish a corrected tag (`vX.Y.Z+1` or
  `vX.Y.(Z+1)`) and state the retraction in the new release notes.
- If a secret was exposed during the release, rotate it, open a private
  security advisory (`SECURITY.md`), and document the exposure window.
